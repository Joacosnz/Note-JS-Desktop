### 1.3 Block State Management & Editor Rendering Loop
- **In-Memory Store**: Managed in `state.activeRecordMap` (`frontend/app.js:4259`), structured strictly as a normalized Notion `recordMap`:
  ```json
  {
    "block": {
      "<uuid>": {
        "role": "editor",
        "value": {
          "id": "<uuid>",
          "type": "text",
          "properties": { "title": [["Content", []]] },
          "content": ["<child-uuid>", ...],
          "parent_id": "<parent-uuid>",
          "parent_table": "block",
          "alive": 1,
          "format": {},
          "version": 1
        }
      }
    }
  }
  ```
- **Rendering Loop**: `renderTreeFromRecordMap(recordMap, rootId, container)` (`frontend/app.js:7263–7316`):
  1. Clears `container.innerHTML = ''`.
  2. Tracks visited IDs in `const visited = new Set()` to prevent infinite loops from circular references (`frontend/app.js:7267`, `7274`).
  3. Skips soft-deleted blocks where `block.alive === 0` (`frontend/app.js:7280`).
  4. If `blockId === rootId`, iterates over `block.content` and renders each child into the container root.
  5. For any block, calls `const blockEl = renderBlock(block)`.
  6. If `block.content` is a non-empty array, resolves the child slot:
     ```javascript
     const childrenSlot = blockEl.querySelector(
       '.notion-block-children, .block-column-content, .notion-column-content, .block-toggle-content, .notion-toggle-content, .block-table-body, .notion-table-body'
     ) || blockEl;
     block.content.forEach(childId => renderSubtree(childId, childrenSlot));
     ```
  7. Mounts `blockEl` into `parentElement.appendChild(blockEl)`.
- **Debounced Persistence Engine**: `persistBlockUpdate(blockId, updates)` (`frontend/app.js:6565–6600`) debounces mutations by 300ms using `pendingBlockUpdates` Map, then flushes via PyWebView bridge `window.pywebview.api.update_block(blockId, updates)` with fallback to REST `PUT /api/blocks/<id>`.

### 1.5 Rich Text Formatting Engine (`properties.title`)
Direct inspection of `frontend/app.js:6218–6450` and `frontend/app.js:6539–6560`:
- `getBlockPropertyHtml(block, propName = 'title')` extracts rich text tuples from `block.properties[propName]` and passes them to `parseRichTextToHtml(tuples)`.
- `parseRichTextToHtml(tuples)` (lines 6218–6304) iterates over tuple segments `[text, decorators]`, rendering:
  - `b` -> `<strong>`
  - `i` -> `<em>`
  - `_` -> `<u>`
  - `s` -> `<s>`
  - `c` -> `<code>`
  - `h` -> `<mark style="..." class="notion-color-${cleanColor}" data-color="${cleanColor}">`
  - `a` -> `<a href="..." target="_blank" rel="noopener noreferrer">`
  - `e` -> `<span class="inline-equation notion-inline-equation inline-katex-node" data-latex="...">`
- `htmlToRichTextTuples(nodeOrHtml)` (lines 6306–6450) parses contenteditable DOM markup back into canonical Notion decorator tuples, cleanly coalescing contiguous segments with identical formatting.
- `handleRichEditorInput(e)` (`frontend/app.js:4849–4875`) catches user input in real-time on any `[contenteditable="true"]`, reads `data-property || 'title'`, invokes `htmlToRichTextTuples(editableEl)`, updates `state.activeRecordMap.block[blockId].value.properties[propName]`, and triggers debounced persistence via `persistBlockUpdate`.

## 2. Logic Chain

1. **Premise 1 (Existing Architecture Foundation)**:
   - The desktop frontend has a functional in-memory Notion `recordMap` tree renderer (`renderTreeFromRecordMap`) and element factory (`renderBlock`).
   - Rich text editing across all contenteditable fields is fully abstracted by `getBlockPropertyHtml` and `htmlToRichTextTuples`.
   - Structural hierarchy is governed by `block.content` arrays on container blocks and `childrenSlot` resolution.

2. **Premise 2 (Missing Block Gap Analysis)**:
   - When a block of type `header_4`, `quote`, `callout`, `to_do`, `transclusion_container`, `transclusion_reference`, `video`, `audio`, `file`, `pdf`, or `bookmark` enters `renderBlock`, it hits the `default:` clause at line 7217, producing a generic `<p class="notion-block block-p">` instead of the required visual component.
   - When a heading block (`header`, `sub_header`, `sub_sub_header`, or `header_4`) has `block.format.toggleable = true`, `renderBlock` produces a flat `<h1/h2/h3>` element without toggle controls or child container slots. Any children in its `content` array fail to render inside a collapsible drawer.

3. **Premise 3 (Rich Text Compatibility)**:
   - Any newly introduced block that represents text (`header_4`, `quote`, `callout`, `to_do`, `bookmark`) can declare `[contenteditable="true"]` with `data-property="title"` (and `caption` for media).
   - Because `handleRichEditorInput` dynamically resolves `data-property`, edits to these blocks will automatically serialize to valid Notion rich text tuples in `properties.title` with full decorator fidelity (`b`, `i`, `_`, `s`, `c`, `h`, `a`, `e`), requiring zero custom serializer code.

4. **Premise 4 (Container vs. Leaf Structural Rules)**:
   - Containers (`quote`, `callout`, `to_do`, `transclusion_container`, and toggleable headers) must include a `.notion-block-children` element in their rendered DOM.
   - Atomic leaves (`header_4` non-toggleable, `transclusion_reference`, `video`, `audio`, `file`, `pdf`, `bookmark`) must have `content: null` and render no child slot.
   - For `transclusion_reference`, since `content` is `null` but it mirrors a `transclusion_container`, `renderSubtree` in `renderTreeFromRecordMap` must resolve `block.format.copied_from_pointer.id`, fetch the container's children from `recordMap.block`, and render them inside the reference's frame.

5. **Premise 5 (Creation & Transactional Protocol)**:
   - In `insertBlockBelow`, when inserting a container block, `content` should initialize as `[]`; when inserting an atomic leaf, `content` should initialize as `null`.
   - The client currently issues two distinct bridge/REST calls (`create_block` and `reorder_block_children`). Aligning with the REA-extracted protocol requires an atomic transaction payload (`op.set` + `op.listAfter`) sent to the backend.
